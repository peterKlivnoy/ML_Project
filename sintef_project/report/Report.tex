\begin{abstract}
We predict, for every hour of a one-week scheduling case and each of the 14 generating units of the
Tokke--Vinje hydropower system, the probability that SINTEF's SHOP optimiser commits the unit. The
work followed two tracks. The first engineered features for gradient-boosted trees: economic
spreads between price and water value, terminal water values, a count model over hours-on per
unit-week, hourly block structure and a long (case, hour, unit) format. It reached 0.9638 micro
ROC-AUC in walk-forward validation and \textbf{0.98058} on the public leaderboard. The second track
starts from the observation that the labels are the output of a known optimisation problem whose
inputs we hold in full: we rebuilt SHOP's weekly problem from the SHOP-ready topology file as a
linear programme and use its solution \emph{only as features} for a learned model. With LightGBM on
top it scores 0.9912 in walk-forward validation, improves every fold and all 14 units over the first
track, and scores \kagglelp{} on the public leaderboard. Four predictor types compared on identical
features (logistic regression, random forest, XGBoost, LightGBM) show that the gain comes from the
optimiser features rather than from the learner.
\end{abstract}

\section{The task and the data}
\label{sec:r-task}

Short-term hydropower scheduling decides, hour by hour, which generating units run and at what
level. SINTEF's SHOP software solves this as a mixed-integer optimisation problem; the InterOpt
project asks whether a machine-learning model can predict SHOP's on/off (unit-commitment)
decisions from the inputs, to speed up or warm-start the optimiser.

The Tokke--Vinje watercourse has 17 reservoirs, 9 plants and 14 units (1{,}000\,MW installed). Each
\emph{case} is a 168-hour week starting at 00:00 UTC; cases start every day, so consecutive cases
overlap by 144 hours. There are 2{,}922 labelled cases (2015-01-01 to 2022-12-31) and 725 test cases
(2023-01-01 to 2024-12-25). The model must output, for each test case, unit and hour, a value in
$[0,1]$: the probability that the unit is on. The metric is micro-averaged ROC-AUC over every
(case, hour, unit) cell --- 6.9M labelled cells and 1.7M test cells --- so probabilities must be
comparable across units as well as ordered within each unit-week.

\subsection{Search domain knowledge}
\label{sec:eda-domain}

We read the task statement, the dataset documentation and the SHOP-format topology file (whose
attributes are defined in the SHOP documentation), and used the standard economics of hydropower
scheduling. The facts that mattered:

\begin{itemize}
\item \textbf{Water value is an opportunity cost.} Water released now cannot be sold later. A unit is
  worth running when the price exceeds the value of the water it uses, the reservoir's
  \emph{water value} (EUR/MWh). The dispatch condition is therefore the \emph{spread} between price
  and water value, not the price alone.
\item \textbf{The week has a boundary condition.} A weekly schedule values the water left at the end
  of the week at the \emph{terminal} water value; the documentation states which day's value that is.
\item \textbf{Starting a unit costs money} (start/stop costs in the topology file), so units run in
  contiguous blocks rather than hour by hour.
\item \textbf{The system is a cascade.} Water released upstream flows into downstream reservoirs and
  plants (Figure~\ref{fig:r-topo}); a plant's decision depends on the reservoirs above and below it.
\item \textbf{Identical units share a penstock} at Tokke (four units) and Vinje (three), so which one
  starts first is a matter of hydraulic losses and tie-breaking, not of different machines.
\item \textbf{Norwegian inflow is dominated by snowmelt} in May--June; reservoirs are drawn down
  through winter and refilled in summer.
\end{itemize}

\subsection{Understand how the data was generated}
\label{sec:eda-generated}

\begin{itemize}
\item \textbf{The labels are optimiser output.} Every case was solved by SHOP v17.17 on the
  Tokke--Vinje model described by the topology file. The labels are therefore a deterministic
  function of the inputs we hold, not noisy observations of the real plant.
\item \textbf{Cases are rolling.} A new case starts every day, so consecutive cases share 144
  wall-clock hours, solved from almost the same state. The same hour solved one day later gets a
  \emph{different} decision 12\% of the time (18\% for Tokke and Vinje; Figure~\ref{fig:r-selfagree}):
  the decision depends on the whole horizon, including the end-of-week boundary, not only on the
  hour. This label self-disagreement explains 78\% of the variance in per-unit difficulty of our first
  baseline. It also means random row splits leak (Section~\ref{sec:r-val}).
\item \textbf{The water values are synthetic} (file name and documentation), one per reservoir per
  day. For a case starting on day $d$ the documentation defines the initial value at $d$ and the
  final (terminal) value at $d+7$ 00:00. We first read the terminal value one day late (log 009) and
  found the off-by-one by rereading the documentation (log 033).
\item \textbf{Two storage series are invented:} Hyljelihyl and Vatjern have no historical records and
  are set to 50\% full throughout.
\item \textbf{The storage series is observed, not planned:} it is the reservoir level at the start of
  each day, so the level at the end of a case reflects decisions taken during it
  (``post-decision'' information, Section~\ref{sec:eda-clean}).
\item \textbf{SHOP's conventions can be recovered from the labels.} Rebuilding the generator
  (Track B, Section~\ref{sec:fe-lp}) required three conventions the documentation does not state ---
  how water values are converted to a value per cubic metre, how river costs are read, how identical
  units are ordered --- and we measured each of them from the labels (Figure~\ref{fig:r-thr}).
\end{itemize}

\subsection{Check if the data is intuitive}
\label{sec:eda-intuitive}

Most series behave as domain knowledge predicts. Inflow peaks in May--June at about 8 times the
winter level, and storage follows the expected annual fill and drawdown
(Figure~\ref{fig:r-inflow-storage}). The system water value tracks price but is much smoother,
as an expected \emph{future} value should be. Commitment has a double-hump daily pattern (trough 0.46
at night, peaks 0.55 at the morning and evening ramps) and almost no weekday pattern
(Figure~\ref{fig:r-hod}).

One fact is counter-intuitive: \textbf{2022 has the highest prices ($\sim$211\,EUR/MWh) and the lowest
on-rate (0.34)} (Figure~\ref{fig:r-year-wv}, left), and raw price correlates \emph{negatively} with
commitment ($-0.19$). The resolution is in the right panel: water values rose with prices, so high
prices did not mean a high \emph{spread}; 2022 was a scarce-water year in which SHOP conserved water.
Measured within each week, price correlates positively ($+0.26$ for the within-week z-score). The
data is consistent once read through the opportunity cost of water.

\subsection{Explore individual features}
\label{sec:eda-individual}

\paragraph{Target.} On-rates range from 26\% (Vinje G3) to 75\% (Lio G1): fourteen differently
balanced problems pooled by one metric (Figure~\ref{fig:r-target}, left). Most unit-weeks are flat:

binary ``constrained'' flag would be constant; the information is in the level and its changes.

\subsection{Training versus test period}
\label{sec:eda-shift}

We measured which past period resembles the test set instead of assuming it: a classifier separates
each half-year's cases from the 2023--24 test cases using case-level inputs (price level,
volatility, negative-price share, water value, spread, fill, inflow). 2021-H2 is the hardest to
separate (AUC 0.785), then 2022-H2 (0.879); every other half-year is above 0.95
(Figure~\ref{fig:r-adv}). We report these two \emph{test-like folds} separately in validation.

\section{Validation methodology}
\label{sec:r-val}

\paragraph{Random splits leak.} A random row split scores 0.957 with the same model that scores 0.835
on a held-out year: rows from one week are near-duplicates, and consecutive weeks share 144 hours at
88\% label agreement. Random \emph{case} splits still inflate by $+0.105$ (log 017). Every number in
this report therefore comes from a temporal split.

\paragraph{Walk-forward.} The reference protocol (logs 024, 028) has six half-year folds from 2020-H1
to 2022-H2; each trains on every case starting before the fold and scores the six months after.
Earlier stages used a single held-out year (2021, the most test-like year, log 020) or four-fold
rolling-origin CV; we judged changes on the per-fold sign pattern, since fold-to-fold variation (SD
up to 0.06) dwarfs most feature effects. A rotating-block scheme was built and rejected: training on
both sides of the held-out block measures interpolation, while the test set requires extrapolation
(log 035). Experiments train on every third case (``stride 3''); submissions train on all cases.

\subsection{Feature extraction II: a first-principles optimiser as a feature generator (Track B)}
\label{sec:fe-lp}

Track A approximated SHOP with hand-made features. But the labels are the output of one
deterministic optimiser, and every input it used is in our data --- the topology file is SHOP-ready.
So we rebuilt the optimisation problem itself (\texttt{src/shoplite.py}; Short notebook 1) and use
its solution as features. The LP is a \textbf{feature extractor only}: its output is never
submitted; every prediction comes from the learned model.

\paragraph{The linear programme.} One per case, the LP relaxation of SHOP's weekly unit-commitment
problem, solved with HiGHS (dual simplex; building and solving take 8\,s per case on one core on
average, 2--25\,s for individual cases; SHOP's own recorded solve times are a median 52\,s, mean
147\,s):
\[
\max\ \sum_t \lambda_t \big(P_t - L_t\big) \;-\; \text{start/stop costs} \;-\; \text{river, bypass, spill costs}
\;-\; \text{penalties} \;+\; \sum_r \omega_r V_{r,T}
\]
subject to hourly water balance in all 17 reservoirs, the Vest-Vassdraget river junction and the
Songa tunnel junction; reservoir bounds; minimum volume and minimum flow (soft, heavily penalised);
for every unit an on/off variable $u\in[0,1]$ carrying the minimum block ($q_{\min}$, $p_{\min}$)
plus segments of the concave envelope of its PQ curve at the case's initial head (turbine efficiency
interpolated between the reference-head curves, times generator efficiency); start/stop variables
with the topology's costs; and main-tunnel and shared-penstock friction $L_t$ as a convex
piecewise-linear cubic in plant flow. $\lambda_t$ is the price and $\omega_r$ the terminal value of
water. The LP's duals give the hourly shadow price of water in each reservoir, from which each unit's
\emph{local water value} (EUR/MWh) and its margin, price $-$ local water value, follow.
Simplifications against SHOP: heads frozen at their initial levels, lossless tunnels between
reservoirs, and an unknown initial on/off state.

\paragraph{Three conventions measured from the labels.} \textbf{Terminal water value:} in weeks where
a unit switches, its on-hour and off-hour prices bracket the threshold SHOP used; regressing that
threshold on terminal water values gives $\approx 1.0\times$ the feeding reservoir's value and
$\approx 0\times$ the downstream value (Figure~\ref{fig:r-thr}; Byrte slope 0.98, $R^2$ 0.99), so one
Mm\textsuperscript{3} in reservoir $r$ is valued as
$\omega_r=\sum_k \mathrm{WV}(\text{reservoir feeding }k)\cdot \mathrm{conv}_k$ over the plants $k$ on
its way to the sea. \textbf{River flow cost:} \texttt{flow\_cost\_curve} read as total cost per hour
(marginal cost = slope) rather than as a marginal cost lifted Kjela's raw AUC from 0.70 to 0.96.
\textbf{Sibling order:} the merit order from the EDA is imposed as
$u_{\text{G1}}\ge u_{\text{G3}}\ge u_{\text{G4}}\ge u_{\text{G2}}$ at Tokke and
$u_{\text{G1}}\ge u_{\text{G2}}\ge u_{\text{G3}}$ at Vinje.

\begin{figure}[H]
\centering
\includegraphics[width=\linewidth]{figures/physics_01_threshold_vs_water_value.png}
\caption{Implied price threshold in every mixed week against the terminal water value of the
reservoir feeding the plant. Points lie on $y=x$: each plant breaks even at its own reservoir's
water value.}
\label{fig:r-thr}
\end{figure}

\paragraph{LP versus MILP as a feature.} Solving with binary $u$ gave a raw AUC of 0.941 against the
relaxation's 0.967 on the same 59-case sample: a 0/1 schedule loses the graded information about how
close each hour is to the margin. The relaxation is the better feature.

\paragraph{The 61 features.} One row per (case, hour, unit):
\texttt{lp\_} --- the LP solution (commitment $u$, power, flow), its temporal context (rolling
windows, run lengths, weekly and daily means, number of units on at the plant), the local water
value and margin, and the reservoir trajectories; \texttt{ec\_} --- price level, rank and z-score
within the week, spread to the terminal water value, season, inflow; \texttt{cn\_} --- the
constraint series; \texttt{st\_} --- the observed storage trajectory; \texttt{s\_} --- unit identity
and static attributes.

\section{Model interpretation}
\label{sec:r-interp}

\subsection{Track A: what the trees learned}

The pruned 15 features are all economic quantities --- spreads, margins, break-even hours, the
share of capacity a spread justifies --- with topology used only to pick \emph{which} water value
and \emph{which} capacity; no raw price, storage, inflow or calendar column survived (log 017). The
single most important feature of the early model, by a factor of 14, was the binary
``price $>$ system water value'': SHOP's dispatch condition, rediscovered
(Figure~\ref{fig:r-imp-a}). In the count model the top feature was the system storage change over
the week --- released water, i.e.\ production --- and the binding-constraint term
$\min(\text{hours of water}, \text{hours profitable})$ (logs 021--022). Hourly-varying features
held 96\% of the gain: micro-AUC rewards ranking hours \emph{within} a week, which a case-level
constant cannot do (log 013).

Third is the margin, price minus the local water value from the LP duals (0.93), with its 7-hour
rolling mean close behind: the learner reads how far each hour sits from the dispatch threshold,
exactly the graded information a binary schedule discards (Section~\ref{sec:fe-lp}). By group, LP
features carry 70\% of the total absolute contribution, economics 15\%, unit identity and static
attributes 13\%, the observed storage trace 2\% and the constraint series 1\%. Economics weigh more
here than in split gain (15\% against 6\% of the gain in the last fold): many small adjustments
rather than a few decisive splits.

\paragraph{The optimiser itself is interpretable.} Its decisions are explained by quantities with
physical meaning: each unit runs when the price exceeds its local water value, which equals its
reservoir's terminal water value unless a constraint binds --- a full reservoir lowers it (water
would otherwise spill), a minimum-flow obligation can force a unit on below it, an empty reservoir
raises it. The three conventions of Section~\ref{sec:fe-lp} are themselves findings about how the
labels were produced.

\section{Discussion}
\label{sec:r-disc}

\paragraph{Why Track B works.} Track A spent most of its effort recovering, through features, a
decision process that is written down: the spread is the dispatch condition, the count is the
weekly water budget, the block structure comes from start costs, the merit order from penstocks.
Solving the actual problem gets all of these at once, consistently across units and reservoirs,
and extrapolates to unseen price regimes (negative prices, the post-crisis level) from physics
rather than from training data. The learner is left with a smaller, more stationary job: the
residual between our simplified replica and SHOP.

\paragraph{Relation to the task's purpose.} InterOpt wants ML to speed up the optimiser. Our best
model still solves an LP, but one roughly 6--18$\times$ cheaper than SHOP's recorded solve times, and its output is a
calibrated commitment probability that could warm-start SHOP's MIP. Unlike Track A's best
features, it needs no post-decision information.

\paragraph{Limitations and next steps.} The remaining errors are fidelity gaps of the replica: heads
frozen at their initial level, Lio's min-flow behaviour, weeks where SHOP runs units below their
water value (e.g.\ 2019-07-09), and degenerate weeks where a reservoir must fill and the timing of
release is arbitrary. Each fix to the replica feeds the learned layer directly. Three conventions
were read off label statistics that include the validation years; they are structural and stable
across years, but the protocol is not blind to them.

\paragraph{What we would do differently.} Read the topology file on day one. Track A's three
largest late gains were corrections found by reading the documentation; Track B is the same lesson
taken to its conclusion.

\section{Reproducibility}
\label{app:repro}

\begin{itemize}
\item \textbf{Configuration.} \texttt{requirements.txt} next to the notebooks pins the package
  versions both notebooks were run with. The notebooks contain all code, start from the raw
  competition files (\texttt{data/kernel}, \texttt{data/extended}, \texttt{sample\_submission.csv},
  \texttt{prediction\_mapping.csv}), need no network and write only intermediate results (the LP
  cache) and the submission file.
\item \textbf{Short notebook 1} (LP + LightGBM): solves the 3{,}647 LPs in parallel ($\sim$2\,h on 4
  cores, cached after the first run), builds features, trains on all labelled cases and writes the
  submission ($\sim$6\,min, peak $\sim$5\,GB RAM). Executed end to end from the raw data, it
  reproduces the uploaded file to $2\cdot 10^{-13}$, and its LP solutions are byte-identical to the
  stored ones.
\item \textbf{Short notebook 2} (XGBoost): builds the hourly table from the raw files, the feature
  stages, the count table and model, the hourly structure and the long format, and trains on all
  labelled cases (about 40\,min on 4 cores; peak $\sim$24\,GB of memory including swap). The long
  design matrix is assembled in place instead of through pandas concatenations; it is verified
  identical to the original assembly, value for value. The uploaded file was produced on an Apple
  Silicon Mac. On x86 Linux with the same package versions the count model's importance ranking
  selects 143 count features instead of 141 (identically at 4 and 8 threads, so not a threading
  effect), and the output correlates 0.995 with the uploaded file, with 98\% of cells on the same
  side of 0.5. We attribute this to platform-level floating-point differences that reorder
  near-tied features; the notebook's last cell reports the comparison.
\item Source modules, every experiment and its result: \texttt{src/}, \texttt{report/leaderboard.md},
  \texttt{report/runs/}.
\end{itemize}
